# Tile Content Materialization Specification

## Overview

The world is procedurally infinite but finitely observed. Every tile exists in
a superposition of possible states until a player first enters it. At that
moment the tile is **materialized** — its content is generated, persisted to
the database, and served to the client. All subsequent visits return the same
persisted content. The world is unique per game seed and accumulates richness
as the player explores.

This document specifies the full materialization pipeline: the trigger, the
content generator interface, the mock implementation, the persistence layer,
the tile image pipeline, and the WebSocket extensions.

---

## Design Principles

1. **Generate once, serve forever** — Content is created on first observation
   and never regenerated. The database is the source of truth.
2. **Deterministic seed, non-deterministic content** — Terrain is deterministic
   (recomputable from address + seed). Content above terrain (NPCs, items,
   descriptions, encounter modifiers) is generated by a pluggable provider
   that may use randomness, AI, or hand-authored data. Once generated, the
   result is persisted and the seed is irrelevant.
3. **Provider interface** — The content generator is an interface. The initial
   implementation is a mock that uses the world seed and terrain type to
   produce basic content. A future implementation will call an LLM. The game
   mechanics are identical regardless of provider.
4. **Depth-aware** — Different depths produce different content. World-tier
   tiles get region-level content (kingdom name, dominant faction). Local-tier
   tiles get ground-level content (NPCs, items, encounter details).
5. **Additive mutations** — Players can add items (`tile_items`) and kill NPCs
   (`tile_npcs` deletion). These mutations layer on top of the generated
   baseline. The baseline is never modified — only the mutable layer changes.

## Data Model

### New Tables

#### `tile_content` — Generated baseline content per tile

```sql
CREATE TABLE IF NOT EXISTS tile_content (
    address       TEXT PRIMARY KEY,
    depth         INTEGER NOT NULL,
    terrain_id    TEXT NOT NULL,
    description   TEXT NOT NULL,
    region_name   TEXT,
    encounter_mod INTEGER NOT NULL DEFAULT 0,
    provider      TEXT NOT NULL DEFAULT 'mock',
    world_seed    INTEGER NOT NULL,
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (address) REFERENCES tiles(address),
    FOREIGN KEY (terrain_id) REFERENCES terrain(id)
);
```

This table records that the tile has been materialized and stores the narrative
description. NPCs and items generated during materialization are inserted into
`tile_npcs` and `tile_items` (which reference this tile by address).

#### `tile_npcs` — Persistent NPCs placed in tiles

```sql
CREATE TABLE IF NOT EXISTS tile_npcs (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    tile_address  TEXT NOT NULL,
    monster_id    TEXT,
    name          TEXT NOT NULL,
    disposition   TEXT NOT NULL DEFAULT 'neutral',
    hp            INTEGER NOT NULL,
    max_hp        INTEGER NOT NULL,
    dialogue      TEXT,
    vendor        BOOLEAN NOT NULL DEFAULT 0,
    generated     BOOLEAN NOT NULL DEFAULT 1,
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (tile_address) REFERENCES tiles(address),
    FOREIGN KEY (monster_id) REFERENCES monsters(id)
);
```

- `generated = 1` means this NPC was created by the content provider during
  materialization. `generated = 0` means it was placed by a game event or
  migration (named NPCs from `npcs.spec.md`).
- Killing an NPC DELETEs the row. The NPC is gone permanently.

#### `tile_items` — Persistent items placed in tiles

```sql
CREATE TABLE IF NOT EXISTS tile_items (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    tile_address  TEXT NOT NULL,
    item_type     TEXT NOT NULL,
    item_id       TEXT NOT NULL,
    quantity      INTEGER NOT NULL DEFAULT 1,
    dropped_by    INTEGER,
    generated     BOOLEAN NOT NULL DEFAULT 1,
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (tile_address) REFERENCES tiles(address),
    FOREIGN KEY (dropped_by) REFERENCES characters(id)
);
```

- `generated = 1` means the content provider placed this item.
- `dropped_by` is set when a player drops an item from inventory.

#### `tile_quest_hooks` — Quest hooks discovered per tile

```sql
CREATE TABLE IF NOT EXISTS tile_quest_hooks (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    tile_address  TEXT NOT NULL,
    description   TEXT NOT NULL,
    quest_type    TEXT NOT NULL,
    difficulty    TEXT NOT NULL DEFAULT 'medium',
    target_address TEXT,
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (tile_address) REFERENCES tiles(address)
);
```

#### `tile_cache` — Cached composite tile images

```sql
CREATE TABLE IF NOT EXISTS tile_cache (
    address       TEXT PRIMARY KEY,
    depth         INTEGER NOT NULL,
    content_hash  TEXT NOT NULL,
    file_path     TEXT NOT NULL,
    generated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_accessed DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (address) REFERENCES tiles(address)
);
```

- `content_hash` is a hash of tile_content + tile_npcs + tile_items for the
  address. When mutations occur (NPC killed, item dropped), the hash changes
  and the cached tile is invalidated on next access.

## Content Provider Interface

```go
type TileContext struct {
    Address      string
    Depth        int
    TerrainID    string
    WorldSeed    int
    ParentTerrain string
    Neighbors    []NeighborInfo
    RegionName   string
    FactionID    string
}

type NeighborInfo struct {
    Address   string
    TerrainID string
    HasContent bool
}

type GeneratedContent struct {
    Description   string
    RegionName    string
    EncounterMod  int
    NPCs          []GeneratedNPC
    Items         []GeneratedItem
    QuestHooks    []GeneratedQuestHook
}

type GeneratedNPC struct {
    Name        string
    MonsterID   string
    Disposition string
    HP          int
    MaxHP       int
    Dialogue    string
    Vendor      bool
}

type GeneratedItem struct {
    ItemType string
    ItemID   string
    Quantity int
}

type GeneratedQuestHook struct {
    Description   string
    QuestType     string
    Difficulty    string
    TargetAddress string
}

type ContentProvider interface {
    Generate(ctx TileContext) (*GeneratedContent, error)
}
```

The interface takes a `TileContext` (everything known about the tile before
content generation) and returns `GeneratedContent` (everything the provider
decided to place there). The service layer persists the result.

## Mock Content Provider

The mock provider uses the tile seed and terrain type to produce deterministic
but varied content. It follows the encounter tables and NPC placement rules
from `game.spec.md`.

### Generation Rules

#### Description Generation

The mock selects from a bank of terrain descriptions keyed by `terrain_id`
and time-independent (the narrator spec handles time-of-day variations at
display time). Each terrain type has 6-8 variants; the tile seed selects one.

#### NPC Placement (depth 2+ only)

| Terrain | Chance (%) | NPC Type |
|---------|-----------|----------|
| road | 25 | Merchant, patrol guard, pilgrim |
| plains | 10 | Farmer, shepherd, wandering cleric |
| grassland | 10 | Herder, hunter |
| forest | 8 | Woodcutter, hermit, ranger |
| dense_forest | 5 | Hermit, wood elf scout |
| hills | 8 | Prospector, dwarf miner |
| mountain | 3 | Mountain hermit, eagle keeper |
| marsh | 5 | Swamp witch, herbalist |
| beach | 12 | Fisherman, beachcomber |
| desert | 3 | Nomad, water seller |
| tundra | 3 | Fur trapper, ice clan scout |

Roll: `seedToFloat(tileSeed, channel=2)` mapped to 0-100. If below the
terrain's chance, place one NPC. NPC type selected by
`seedToFloat(tileSeed, channel=3)` index into the type list.

NPCs placed by the mock have:
- Name: selected from a name bank seeded by tile address
- MonsterID: null (non-combat social NPCs)
- Disposition: friendly or neutral (never hostile — hostile creatures come
  from encounter rolls, not materialization)
- HP/MaxHP: 4/4 (commoner)
- Dialogue: one line selected from a terrain-appropriate bank
- Vendor: true for merchants, false for others

#### Item Placement (depth 2+ only)

| Terrain | Chance (%) | Item Type |
|---------|-----------|-----------|
| road | 5 | Lost coin purse (1d6 gp), broken wheel spoke |
| forest | 8 | Fallen branch (staff), wild herbs |
| hills | 10 | Loose stones, iron ore fragment |
| marsh | 6 | Rotting rope, glass vial |
| beach | 15 | Driftwood, sea shell, washed-up crate |
| mountain | 5 | Quartz crystal, iron spike |
| desert | 3 | Bleached bones, half-buried flask |
| ruins (tagged) | 40 | Pottery shard, rusty dagger, old coin |

Items placed by the mock use existing `items` table entries where possible,
falling back to flavor items with no mechanical effect.

#### Quest Hook Placement (depth 1-2 only)

At world and regional depth, the mock can place quest hooks based on the
region and terrain:

| Condition | Quest Hook |
|-----------|-----------|
| Near forest border | "Woodcutters report strange sounds deeper in" |
| Near mountain | "An old mine entrance, partially collapsed" |
| Near road intersection | "A signpost with a torn bounty notice" |
| Near water | "Fishermen speak of something in the deep" |

Quest hooks are informational — they point the player toward content that
will be materialized when they arrive at the target tile.

#### Encounter Modifier

The mock sets `encounter_mod` based on terrain danger:

| Terrain | Encounter Mod |
|---------|--------------|
| road | -1 |
| plains, grassland, beach | 0 |
| forest, hills | 0 |
| dense_forest, marsh | +1 |
| mountain, desert, tundra | +1 |

This modifier adds to the encounter check roll (per `game.spec.md` §5).

## TileContentService

```go
type TileContentService struct {
    db       *sql.DB
    provider ContentProvider
}

func NewTileContentService(db *sql.DB, provider ContentProvider) *TileContentService

func (s *TileContentService) GetOrMaterialize(address string, worldSeed int) (*TileContentResult, error)

func (s *TileContentService) GetContent(address string) (*TileContent, error)

func (s *TileContentService) GetNPCs(address string) ([]TileNPC, error)

func (s *TileContentService) GetItems(address string) ([]TileItem, error)

func (s *TileContentService) GetQuestHooks(address string) ([]TileQuestHook, error)

func (s *TileContentService) IsMaterialized(address string) (bool, error)
```

### `GetOrMaterialize` Flow

```
1. SELECT FROM tile_content WHERE address = ?
2. If exists → load NPCs, items, quest hooks → return
3. If not exists:
   a. Load tile from tiles table (terrain_id, depth)
   b. Load parent terrain
   c. Load neighbor addresses and their terrain/content status
   d. Look up region name from world coordinate mapping
   e. Build TileContext
   f. Call provider.Generate(context)
   g. BEGIN TRANSACTION
      - INSERT INTO tile_content
      - INSERT INTO tile_npcs (for each generated NPC)
      - INSERT INTO tile_items (for each generated item)
      - INSERT INTO tile_quest_hooks (for each hook)
      COMMIT
   h. Return the newly persisted content
```

### Concurrency

If two players enter the same unmaterialized tile simultaneously, `INSERT OR
IGNORE` on `tile_content` ensures only one materialization wins. The loser's
transaction sees the existing row and returns it. The `tile_content.address`
primary key prevents duplicate generation.

## WebSocket Extensions

### New Message Types

#### `get_tile_contents` — Retrieve everything at the player's current tile

```json
→ {"type": "get_tile_contents", "payload": {"character_id": 1}}
← {"type": "tile_contents", "payload": {
     "address": "map2_35_07",
     "description": "Tall grass parts around a worn footpath...",
     "terrain_id": "grassland",
     "region_name": "Golden Plains",
     "encounter_mod": 0,
     "npcs": [
       {"id": 14, "name": "Davin the Shepherd", "disposition": "friendly",
        "dialogue": "Fair day. Watch for wolves past the ridge.", "vendor": false}
     ],
     "items": [
       {"id": 7, "item_type": "item", "item_id": "rations", "quantity": 1}
     ],
     "quest_hooks": []
   }}
```

#### `talk_to_npc` — Interact with a specific NPC

```json
→ {"type": "talk_to_npc", "payload": {"character_id": 1, "npc_id": 14}}
← {"type": "npc_dialogue", "payload": {
     "npc_id": 14,
     "name": "Davin the Shepherd",
     "dialogue": "Fair day. Watch for wolves past the ridge.",
     "disposition": "friendly",
     "vendor": false
   }}
```

#### `drop_item` — Drop an item from inventory into the current tile

```json
→ {"type": "drop_item", "payload": {"character_id": 1, "equipment_id": 7, "quantity": 1}}
← {"type": "drop_result", "payload": {"success": true, "tile_item_id": 42}}
```

#### `pick_up_item` — Pick up an item from the current tile

```json
→ {"type": "pick_up_item", "payload": {"character_id": 1, "tile_item_id": 42}}
← {"type": "pick_up_result", "payload": {
     "success": true,
     "item_type": "item",
     "item_id": "rations",
     "quantity": 1
   }}
```

### Modified Existing Messages

#### `move` — Now triggers materialization

The `handleMove` handler gains an additional step after `GetOrCreate`:

```
existing:  tileService.GetOrCreate(newAddress, worldSeed)
new:       tileContentService.GetOrMaterialize(newAddress, worldSeed)
```

The `MoveResultPayload` gains new fields:

```go
type MoveResultPayload struct {
    // ... existing fields ...
    Description   string        `json:"description"`
    RegionName    string        `json:"region_name,omitempty"`
    EncounterMod  int           `json:"encounter_mod"`
    NPCCount      int           `json:"npc_count"`
    ItemCount     int           `json:"item_count"`
    QuestHookCount int          `json:"quest_hook_count"`
}
```

The full NPC/item/quest details are NOT included in the move response (too
heavy). The client uses `npc_count > 0` as a signal to fetch `get_tile_contents`
if the player wants to interact.

#### `zoom_in` — Now triggers materialization for all siblings

When zooming in, all 100 sibling tiles are materialized (they're already created
by `MaterializeChildren`). This pre-populates content for the visible area so
the client can show indicators.

## Tile Image Pipeline

### Base Tiles (Static)

The pre-rendered tile pyramid in `map_tiles/map2/` serves as the static
geographic base layer. These tiles show terrain but no dynamic content. They
are served as static files.

### Content Overlay (Dynamic)

Dynamic content (NPC markers, item glints, quest indicators, fog-of-war) is
rendered as an overlay by the client, not baked into the base tile.

The server provides content data via WebSocket. The client composites:

```
Layer 0: Pre-rendered base tile (from map_tiles/)
Layer 1: Fog of war mask (from explored_tiles)
Layer 2: Content markers (from tile_contents response)
Layer 3: Time-of-day tint (from game_hour)
Layer 4: Player token
```

This avoids server-side image generation entirely. The Go server never needs
ImageMagick or image libraries. The Godot client handles all rendering.

### Future: Server-Side Tile Composition

If a future content provider generates visual content (custom terrain art,
building sprites, NPC portraits), the server can optionally composite tiles
using Go's `image/draw` package:

```go
import (
    "image"
    "image/draw"
    "image/png"
)
```

Go's standard library supports PNG/JPEG read/write, image compositing, and
basic drawing. No external dependencies required. This is reserved for a
future phase and is not part of the initial implementation.

## Tile Cache Invalidation

When the mutable layer changes (NPC killed, item dropped/picked up), the
client must know to refresh its overlay:

1. The server tracks a `content_version` counter per tile address
2. On any mutation (NPC delete, item insert/delete), increment the version
3. The `tile_contents` response includes `content_version`
4. The client caches content keyed by `(address, version)`
5. On re-entering a tile, the client sends its cached version; if it matches,
   the server returns a `304`-equivalent "no change" response

```json
→ {"type": "get_tile_contents", "payload": {"character_id": 1, "cached_version": 3}}
← {"type": "tile_contents_unchanged", "payload": {"address": "map2_05_07", "version": 3}}
```

## Migration

A new migration adds the tables and seeds any hand-placed named NPCs from
`npcs.spec.md`:

```
migrations/YYYYMMDDHHMMSS_tile_content_materialization.sql
```

Contents:
1. `CREATE TABLE tile_content`
2. `CREATE TABLE tile_npcs`
3. `CREATE TABLE tile_items`
4. `CREATE TABLE tile_quest_hooks`
5. `CREATE TABLE tile_cache`
6. `INSERT` named NPCs from `npcs.spec.md` into `tile_npcs` with
   `generated = 0` at their specified tile addresses

Named NPCs are placed at fixed addresses derived from their settlement's
world coordinates (from `world.spec.md`). They exist before any player
visits the tile — they are not generated by the content provider.

## Invariants

1. A tile in `tile_content` is never deleted or regenerated
2. A tile not in `tile_content` has no NPCs, items, or quest hooks (except
   hand-placed named NPCs from migrations)
3. `tile_npcs` rows with `generated = 0` survive independent of materialization
4. The `ContentProvider.Generate` method is called exactly once per tile
   address per game — ever
5. Terrain is always deterministic from `(address, worldSeed)` — the content
   provider does not change terrain, only populates it
6. The client never generates content — it only renders what the server
   provides
7. Multiple simultaneous materializations of the same tile produce identical
   database state (idempotent via `INSERT OR IGNORE`)
